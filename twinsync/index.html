TwinSync：Windows 双向文件同步的设计与实现

发表于2026-11-16|更新于2026-11-16|项目实践
|总字数:4.7k|阅读时长:17分钟|浏览量:

TwinSync 是一个 Windows 双机文件同步工具。指定两台电脑的某一个文件夹，配对后自动后台同步。

项目地址：https://github.com/NimbusFan/TwinSync

运行结构与使用范围

TwinSync 面向 Windows 10/11，依赖 .NET Framework 4.7.2 或更高版本。两台电脑各自运行后台进程，直接交换文件清单和内容；管理页面默认通过 http://127.0.0.1:55220 访问。

图 1：管理界面和同步核心分开运行。两端通过共享文件夹 ID 对应同一组内容，本地目录可以不同。

例如，电脑 A 选择 D:\Work\Notes，电脑 B 选择 E:\Shared\Notes，两者仍能建立同一组同步关系。设备之间不需要约定相同的盘符，也不会把对方传来的绝对路径直接当成本机写入位置。

这套结构不要求额外部署中央文件服务器，但要求设备之间网络可达。局域网发现可以帮助填写地址，不负责跨越 NAT，也不提供云端中继。电脑离线期间，另一端的编辑先保留在本机，等双方恢复连接后再核对。

后台运行依附于当前 Windows 用户会话，登录启动使用当前用户的启动项；它不是安装成系统服务后、无需用户登录就运行的模式。浏览器退出与后台进程退出，也需要区分。

图 2：仓库中的管理界面示例，使用演示数据。文件数量与容量用于展示界面，不是吞吐量测试结果。

首次安装与双机配置

安装包和源码包放在 GitHub Releases。核对时最新公开预发布版本为 v1.0.0-beta.2，属于测试版本。

文件 用途
TwinSyncSetup.exe 在两台 Windows 电脑上安装和使用
TwinSync-source.zip 查看源码、文档、回归用例并自行构建

首次运行需要分别为两台电脑命名。接着在设备页查看对端地址、端口、完整设备指纹和一次性配对码，核对指纹后完成配对。最后添加文件夹，选择同步方向及共享设备；接收方收到邀请后，要在自己的电脑上选择目录并确认。

同步方向按本机视角理解：

模式 本机行为
双向 根据双方文件状态发送或接收变更
仅发送 发送本机变更，拒绝远端写入和删除
仅接收 不主动向对端推送本机变更；本地编辑仍需参与状态核对

“仅接收”不等于把文件夹变成只读，也不等于每轮无条件覆盖本地内容。两个设备的方向设置需要一起看，否则可能出现一边希望发送、另一边又拒绝接收的情况。

首次验证用一个测试目录即可：新建文件、修改内容、断开连接后再恢复，最后测试删除和双方编辑。尤其要记住，同步会传播被授权的删除，不能代替独立备份。安装和日常操作的完整步骤见项目使用指南。

文件变化的检测与增量扫描

一个直观实现是定时递归整个文件夹，再计算所有文件的哈希。它容易理解，但目录变大后，即使只修改一个小文件，也可能反复遍历大量无关路径。

TwinSync 将变化检测拆成两步：FileSystemWatcher 提供待核对的路径，扫描器再读取磁盘状态并更新索引。事件回调不直接执行文件同步。

图 3：事件用于缩小核对范围，索引和磁盘内容才参与后续同步决策。箭头表示处理顺序，不代表每一步都在同一线程中完成。

ScanQueue 用不区分大小写的集合收集路径，同一路径多次变化只需进入一次待扫描集合。扫描时还会合并嵌套范围：如果已经要检查整个子目录，就不必再对其中每个文件单独发起一次遍历。

重命名同时加入旧路径与新路径。当前索引以相对路径标识文件，因此重命名通常表现为旧路径删除、新路径出现；它没有独立的文件身份追踪，不能据此承诺重命名一定零传输。

文件事件也不能承担完整性保证，所以实现中保留了全量核对的退路：

  • 监听器报错、配置变化或队列积累过多时，标记下一轮全量扫描。
  • 监听正常时，仍以约 600 秒为阈值安排全量核对；监听不可用时缩短到约 30 秒。
  • 手动同步要求全量核对；扫描失败后，待处理范围会重新放回队列。

这里的“全量扫描”指遍历整个目录，不必然意味着重新哈希每个文件。普通扫描会用长度与修改时间判断能否复用已有哈希；针对事件路径的扫描则要求重算内容哈希。元数据可以减少读取开销，却不能证明内容永远没有变化。

这种设计把平时的开销集中到变化路径，同时为遗漏事件保留周期性核对。具体实现见 ScanQueue.cs 与 Scanner.cs。

文件索引与同步决策

内容、版本和删除标记

同步需要知道的不只是文件是否存在。当前索引记录了以下关键字段：

字段 含义
path 相对共享目录的路径
hash、size 文件内容的 SHA-256 与字节数
mtimeMs 文件修改时间，用于元数据判断及可选的冲突策略
rev、origin 逻辑修订号及产生该版本的设备
baseHash 用于判断本地内容是否变化的比较基线
deleted 删除标记，表示这条路径有需要传播的删除状态

删除不能简单实现成“把条目从索引移除”。否则，对端只能看到本机没有这个文件，无法区分它是尚未接收过，还是已经被明确删除。TwinSync 保留删除条目，更新修订号，并记录删除前的内容基线。

清单比较与目录方向

每轮核对取得对端文件清单，再对两边的路径取并集。每条路径根据内容、版本次序与目录模式，得到四类动作：

动作 含义
same 内容一致或双方均已删除，更新必要的确认信息
push 将本机文件或删除状态发给对端
pull 接收对端文件或删除状态
none 目录方向不允许执行本轮传输

普通版本排序依次比较 rev、origin、hash，给相同修订号的不同版本一个稳定次序。修改时间主要在双方都修改、且选择“较新版本”策略时参与比较。

稳定排序解决的是“两边如何作出一致选择”，不代表程序知道哪个版本更符合用户意图。rev 也不是实际时间，更不能仅凭数值较大就宣称它具有完整的因果信息。当前实现没有使用版本向量或文本三方合并，状态判断应在这个范围内理解。同步决策实现

默认策略是保留冲突副本。接收较高次序的版本时，如果本机还有未确认修改，就先保留本机内容，再更新原路径并登记冲突。被拒绝的传入版本也可能产生需要处理的冲突记录，因此状态页需要展示冲突，不能把“所有任务执行完”直接等同于“没有需要用户处理的问题”。

项目还提供按修改时间选择较新版本的策略。它适合用户明确接受这一规则的场景，但受两台机器的时钟影响；时间相同时仍需要稳定的比较规则。它无法理解“新增了一个关键参数”和“删掉了一段内容”哪个更重要。

对文档和代码，保留副本通常比直接丢弃一边内容更容易事后处理。不过，冲突副本只是保留材料，不是自动合并结果；用户仍要比较内容并作出选择。

分块传输与断点续传

较大的文件传到一半断网，如果每次都从头发送，重连成本会随文件大小增加。TwinSync 将新版设备之间的传输拆成最大 4 MiB 的校验块，记录已确认的位置。

续传不能只看临时文件有多大。一个有效的续传位置至少要满足：对应同一份目标内容，之前的分块已校验并落盘，而且接收权限仍然有效。

图 4：传输完成和正式文件提交是两个阶段。分块进度不能直接当作最终写入成功。

上传时，接收端检查块的位置、长度和 SHA-256，写入临时文件并刷新到磁盘后，才保存新的续传位置。某一块中断或校验失败，就退回该块开始前的位置，不确认已经收到的半块内容。

下载时使用 HTTP Range 请求指定区间，并验证响应区间和分块哈希。重连会重新核对已完成内容的前缀，全部接收后还要验证完整文件的 SHA-256。

这带来一个明确的取舍：校验前缀需要重新读取部分磁盘内容，可以避免拿错误的临时文件继续拼接，但不是免费的恢复操作。分块也不等于差分同步：当前机制主要复用同一次内容传输中已经确认的部分，并不按相似块计算两份不同文件之间的最小字节差异。

临时网络故障采用 1、2、4 秒间隔、最多三次自动重试；认证、授权和内容校验错误不会靠无限重试解决。传输状态还绑定文件内容、设备凭据和共享授权，暂停、撤销共享或更改目录后，旧任务不能直接沿用原授权提交。续传接收端 · 传输客户端

正式文件的提交保护

一次传输里，最值得谨慎处理的是最后一次写入。即使远端内容完全正确，也不能直接覆盖目标路径：从扫描到传输完成的这段时间，本机文件可能又被编辑过。

AtomicFile 将正式提交集中处理，主要检查三件事：

  1. 临时文件的完整哈希与预期内容一致。
  2. 正式文件仍是本轮预期的本地版本；原本不存在的路径也不能突然出现其他内容。
  3. 当前设备、目录及写入操作仍有授权。

已有正式文件通过 File.Replace 替换，新文件通过 File.Move 提交。覆盖路径还会根据版本设置保存历史内容；替换失败时，不退回“先删除旧文件，再移动新文件”的做法。

后者看似是兼容性处理，却把一次失败变成了数据缺失：删除旧文件之后，如果移动新文件又失败，原位置将两份内容都没有。宁可明确报告失败、保留旧文件，也不应把这个风险藏在正常同步流程中。

传输过程中撤销共享也是类似问题。任务创建时通过过权限检查，并不能证明几秒后仍有权限。实现使用授权代次和传输绑定，在分块处理及最终写入时重复检查；重新启用共享，也不会让旧任务的授权重新有效。文件提交实现

这种保护覆盖的是单文件提交，不是整个文件夹的事务。批量同步可能一部分成功、一部分失败，状态应保留失败路径和原因，后续按原范围处理。不能因为最后一个文件成功，就把整轮记录成成功。

配对、共享与本机管理

设备发现、设备信任和目录授权是三个步骤。发现列表只能说明网络中出现了某个设备，不能直接允许它读取文件。

TwinSync 在局域网通过 UDP 55221 发布设备标识、名称与服务端口，发现包不携带配对码、令牌或本机目录。连接时使用 TLS 1.2，并固定核验完整的 SHA-256 证书指纹。指纹需要通过可信渠道核对，不能把尚未信任的网络响应当成它自己的可信证明。

一次性配对码为六位、有效期十分钟，成功配对后轮换。配对建立设备关系，文件夹共享还需要用户单独确认：邀请只包含文件夹标识和显示信息，接收方自行选择本机目录。

权限检查放在服务端，覆盖清单、读取、写入和删除等操作。路径校验拒绝父目录跳转、绝对路径和不允许的特殊路径，并检查符号链接或目录联接，避免请求通过授权目录中的跳转绕到其他位置。

浏览器管理页则有另一组边界：默认只允许本机管理，检查 Host、Origin 与 CSRF 令牌。证书私钥及设备令牌由当前 Windows 用户的 DPAPI 保护；这不等于同步文件和历史版本已经加密，也不意味着整个身份数据目录可以直接复制到另一台电脑使用。

这些机制的目标是收紧程序能够读取、写入和信任的范围，并非保证本机不会被控制。当前项目尚未经过独立安全审计，完整的保护范围与限制见安全说明。

索引存储与性能取舍

当前索引保存在 JSON 中，运行时用不区分大小写的字典按路径查找。这个方案依赖少、文件便于检查，但目录规模增长后，序列化和内存占用都需要单独测量。

项目已经将索引保存改为流式写入，避免保存时再深拷贝一整份条目、再生成完整 JSON 字符串。加载时也解除解析数组对条目的容器关联，减少旧快照被间接保留。

仓库的性能记录保留了一次 10,000 条合成索引的隔离测量：

指标 原实现 流式保存实现
保存后托管内存 68.10 MiB 40.46 MiB
单次保存时间 92 ms 27 ms

这组数据只说明当时那个索引测试程序中的变化。内存是在测试程序执行垃圾回收后读取的托管堆数值，保存时间是单次观察；它们不是整个应用的工作集，也不能推导出双机同步速度提高了多少。

同样，管理页面使用浏览器，前台动画的开销应与后台同步进程分开看。关闭网页能消除该页面的动画开销，却不会消除扫描文件、计算哈希和传输内容的成本。后续更有价值的测量包括真实文件分布下的扫描时间、长时间传输峰值，以及大量小文件时的索引保存成本。

源码构建与回归验证

源码构建使用 Windows 的 C# 编译器，不需要 npm 或在线恢复前端依赖。仓库同时保留了同步、安全、安装和工作流回归脚本：

输出为 dist/TwinSyncSetup.exe 与 dist/TwinSync-source.zip。运行前需要具备项目要求的 Windows 与 .NET Framework 环境。

对同步工具，值得长期保留的用例是失败发生时的数据状态：

  • 两端指向不同本机目录，仍能正确共享同一组内容。
  • 修改时间与修订号次序相反时，冲突策略仍按约定执行。
  • 传输中断后，只有完成校验的分块可以续用。
  • 覆盖前本机发生新编辑，正式文件得到保留。
  • 传输途中暂停或撤销共享，旧任务不能在重新授权后继续提交。
  • 原子替换失败、版本恢复失败或部分文件失败时，界面返回可定位的结果。

这些场景已有对应回归覆盖，但测试存在不等于所有真实环境都已经验证。当前实现仍受 Windows 文件系统、网络可达性和文件状态模型约束；它没有提供跨平台客户端、云端中继或自动文本合并。

TwinSync 的核心取舍，是把同步拆成可以核对的几个阶段：检测变化、判断状态、传输内容、验证条件，最后才提交文件。这样在网络中断、双方编辑或权限变化时，程序可以说明本轮做到了哪里，以及为什么没有继续覆盖。
