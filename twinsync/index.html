TwinSync：一个自己开发的轻量级 Windows 双机文件同步工具

发表于2026-11-18|更新于2026-11-18|项目实践
|总字数:4.6k|阅读时长:17分钟|浏览量:

平时在工位的电脑和自己的笔记本之间切换干活时，同步工作目录一直是个很头疼的问题。用网盘同步有限速，还得把私人文件传到第三方服务器；用开源工具界面太丑；用windows自带的文件夹同步，配置起来又很麻烦。于是决定自己写一个工具——TwinSync诞生。

项目已开源：https://github.com/NimbusFan/TwinSync

一、TwinSync 是什么？

一句话概括：TwinSync 是一个面向 Windows 10/11 的点对点（P2P）双机文件夹同步工具。只需要在两台电脑上各自指定一个文件夹，完成一次安全配对，就能在后台自动保持数据一致。

在设计时定下了四个核心原则：

  1. 零中心服务器，点对点直连：两台电脑直接通过局域网或可达网络交换文件清单与数据块，不经过云端中继，不需要注册额外的同步账号。
  2. 原生运行时，离线构建：后端同步引擎基于 C# 与 .NET Framework 4.7.2 开发，构建源码直接调用系统自带的 C# 编译器，无需安装 Node.js。JSON 库等依赖随项目提供，不需要在线恢复。
  3. 前后端分离的本地 Web 控制台：后台守护进程静默执行同步，管理界面通过浏览器访问本地 http://127.0.0.1:55220 打开。关闭浏览器页面不影响后台继续同步。
  4. 本地目录路径解耦：两端通过共享的 Folder ID 关联同一组文件，而不绑定绝对路径。电脑 A 的 D:\Work\Notes 可以直接和电脑 B 的 E:\Shared\Notes 双向同步，不受盘符差异影响。

二、快速上手：三步跑通双机同步

可以在项目的 GitHub Releases 页面下载安装包。截至 2026 年 11 月 18 日，最新发布版本为 v1.0.0-beta.6：

  • TwinSyncSetup.exe：标准安装包，在两台 Windows 电脑上直接安装即可；
  • TwinSync-source.zip：完整源码、回归测试脚本与架构文档。

安装完成后，只需三步即可建立同步：

  1. 设备发现与安全配对：在两台电脑上分别打开 http://127.0.0.1:55220，为本机起个设备名。TwinSync 会通过局域网 UDP 55221 广播发现彼此，连接时通过 TLS 1.2 + 完整 SHA-256 证书指纹核验 + 6 位一次性配对码（10 分钟有效） 建立信任。
  2. 发起与接受文件夹共享：在电脑 A 添加要同步的目录并选择共享对象；电脑 B 收到邀请通知后，在自己的磁盘上选定对应存放目录并确认。
  3. 选择同步方向：每个共享目录都可以按本机视角灵活配置同步策略：
同步模式 本机行为说明 适用场景
双向（Bidirectional） 推送本机变更，同时接收远端变更；双方修改时按冲突策略处理 日常主力机与笔记本协同办公
仅发送（Send Only） 只向对端推送本机修改，拒绝远端写入或删除 主机向备份机单向分发资料
仅接收（Receive Only） 不主动向对端推送本机变更，仅作为接收端参与状态核对 镜像接收特定目录内容

(注：同步工具会如实传播已授权的删除操作，它解决的是多端一致问题，不能替代冷备份。)

设备页：查看本机连接信息，核对指纹后与另一台电脑配对。

查看文件浏览与空间分布界面

文件页：本机同步文件夹、当前目录和共享设备分开显示，待确认的邀请单独列出。

空间分布：按目录查看文件占用，点击色块继续浏览下一层。

升级时，两台电脑都需要更新：先从托盘退出旧服务，再运行安装包，随后刷新管理页面。新的运行记录和统计从新版开始保存，旧版本没有记录的信息无法事后补回。

三、核心架构

下面介绍 TwinSync 内部的五个设计模块。

1. 增量扫描与兜底机制

如果每次都傻瓜式地遍历整个文件夹并重算所有文件的 SHA-256，目录一大会把磁盘 I/O 打满。TwinSync 把变化检测拆成了 “事件捕获 + 队列合并 + 按需哈希” 三个阶段（对应源码 ScanQueue.cs 与 Scanner.cs）：

图 3：TwinSync的流水线

  • 路径去重与范围合并：FileSystemWatcher 监听到变更后不直接触发传输，而是将路径加入大小写不敏感的 ScanQueue。同一批待扫描范围中的重复路径会去重；如果其中已经包含父目录，就不再单独遍历它的每个子路径。
  • 元数据快速跳过：全量遍历时，如果文件长度与修改时间（mtimeMs）没有变化，可以复用索引中的历史 SHA-256；针对事件路径的扫描则强制重算哈希。元数据检查用来减少磁盘读取，不能代替内容校验。
  • 周期性全量兜底：监听正常时，以 600 秒 为阈值安排全量核对；监听不可用时缩短到 30 秒。监听器报错会直接标记下一轮全量扫描，不必等待周期到达。全量核对指遍历完整目录，并不意味着每次都强制哈希全部文件。

2. 索引结构、墓碑删除与冲突保留

为了准确判断两端谁新谁旧，TwinSync 在本地为每个文件维护了一条完整的状态索引（实现见 SyncModel.cs）：

索引字段 作用说明
path 相对于共享根目录的标准化路径
hash / size 文件内容的 SHA-256 摘要与字节大小
rev / origin 逻辑递增修订号与产生该修订的设备标识
baseHash 当前内容的比较基线：扫描产生新版本时记录前一内容哈希，同步确认后更新为确认内容
deleted 墓碑标记（Tombstone）：删除文件时不直接抹掉索引条目，而是保留记录并置为 true，从而把“删除动作”准确传播给对端

当两台电脑离线时修改了同一个文件怎么办？

假设双端原本共同确认了版本 h0，随后在断网状态下各自修改：

重连比对清单时，程序会检测到 local.hash != remote.hash，且两边都偏离了各自的 baseHash，从而触发 BothChanged 冲突判定。
TwinSync 默认采用保留冲突副本的策略：接收较高逻辑次序的版本时，先保留本机未确认的修改，再更新原路径并登记冲突，交由用户比对。也可以切换为“按较新修改时间胜出”，但这个选择受设备时钟影响，不代表程序理解哪一份内容更重要。

baseHash 是这里的比较依据，不是完整保存的共同祖先；逻辑修订号提供稳定次序，也不能单独还原多端因果关系。当前实现不做文本三方合并。

3. 4 MiB 分块传输与断点续传

传输几个 G 的大文件时如果 Wi-Fi 闪断，从头重传非常折磨人。TwinSync 实现了基于 4 MiB 校验块 的断点续传机制（见 ResumableTransfers.cs 与 PeerClient.cs）：

图 4：分块校验、断点恢复与原子提交的两阶段

  • 逐块落盘确认：每传输完一个 4 MiB 数据块，接收端都会校验偏移量、长度和分块 SHA-256，强制 Flush 写入临时文件后才推进已确认进度；如果某块传到一半断开，重连时直接从上一块的确认边界续传。
  • 带退避的网络重试：遇到临时网络抖动时，客户端按 1s -> 2s -> 4s 间隔自动重试最多 3 次；而遇到权限撤销、证书校验失败或内容哈希不匹配时则停止自动重试并返回原因，避免无意义的死循环。
  • 恢复前前缀复核：断点恢复时，接收端会先核验临时文件已落盘部分的哈希与目标文件版本、当前共享授权是否仍然有效，杜绝“张冠李戴”拼接出损坏文件。

4. 原子文件提交与权限代次防护

文件传输完毕后，最后一步“写入正式路径”其实是最危险的，如果在传输的这几秒里，用户在本地又编辑了目标文件，或者在网页上点击了“取消共享”，直接覆盖就会造成数据丢失。

为此，我在 AtomicFile.cs 中设计了三道提交防线：

  1. 全量哈希复验：临时文件接收完毕后，必须通过完整文件的 SHA-256 校验，才允许进入提交阶段。
  2. 乐观并发检查 + 原生原子替换：提交瞬间再次核对目标路径的当前磁盘状态是否仍等于本轮任务开始前的预期版本（防止覆盖用户刚保存的新内容）。校验通过后，已存在文件调用 Windows 原生 File.Replace 原子替换（同时按设置保留历史版本备份），新文件调用 File.Move 落位；如果原子替换因文件被占用而失败，宁可报错等待下一轮，也绝不采用“先删旧文件再移入新文件”这种会导致数据真空的危险做法。
  3. 授权代次绑定（Generation Token）：暂停同步、撤销设备或修改目录共享范围时，都会让原有授权代次失效。即使传输任务在几秒前合法启动，只要中途用户暂停了同步或撤销了共享，最终提交时的代次校验就会立刻拦截该写入，重新开启共享也不会让残留的旧任务复活。

5. 安全边界与索引序列化优化

  • 设备通信与本机管理防护：局域网发现包只包含设备 ID、名称与服务端口，不包含配对码或目录路径；设备私钥与访问令牌使用当前 Windows 用户的 DPAPI 保护；Web 管理端默认仅允许本机访问，并校验 Host、Origin 与 CSRF Token。管理访问限制与设备间 TLS 通信分开处理。DPAPI 不会加密同步文件或历史版本，完整边界见 docs/security.md。
  • 流式 JSON 索引写入：早期版本在保存文件索引时，会先深拷贝整份字典再拼接完整的 JSON 字符串，目录文件一多内存峰值就很明显。后来我把索引持久化改造成了流式序列化写入，并在加载时及时解除解析数组对条目对象的引用。在 10,000 条记录的基准测试中（见 docs/performance.md），性能提升非常直观：
指标（10,000 条索引测试） 优化前 流式写入优化后 改善幅度
保存后托管堆内存 68.10 MiB 40.46 MiB -40.6%
单次索引保存耗时 92 ms 27 ms -70.7%

这组数值来自早期一次隔离测量：内存在测试程序执行垃圾回收后读取，时间为单次观察值。它说明当时的索引保存开销变化，不代表当前整个进程的内存峰值或双机传输吞吐量。

四、实际使用中的几个边界

后续这几轮修正，大多发生在同步已经开始、磁盘或用户操作又改变了状态的时候。文件清单只能描述某个时刻，任务执行到一半时，还得重新判断它是不是有效。

1. 续传任务需要有明确的退出路径

早期的问题不只是临时文件没删干净。空任务、已经失效的任务继续占着续传名额，积累到一定数量后，后面的正常文件也进不来。单纯提高队列上限，只会把问题推迟。

现在上传和下载的临时内容统一放进同步目录下隐藏的 .twinsync-cache，由所有权标记确认这是应用自己的缓存。扫描、共享访问和目录迁移都会排除它，避免临时内容再次进入同步。

缓存按状态处理，而不是一到时间就整目录删除：

任务或缓存状态 处理方式
网络中断，但内容和授权仍有效 保留已确认分块，等待续传
空任务、临时文件缺失、内容或授权已失效 回收对应记录与缓存，释放名额
正式文件已经提交成功 清理已完成的传输缓存
最终写入失败 结束该上传任务并释放缓存，不让失败任务长期占位
无法关联到有效任务的旧版临时数据 按归属规则隔离，保留七天后再清理

启动时会做一次恢复检查，后台也约每三十秒检查一次。有效的旧断点会迁移到新缓存目录；普通文件和没有应用所有权标记的内容，不在回收范围内。对应实现是 TransferCache.cs 与 ResumableTransfers.cs。

2. 目录删除后，旧任务不能把它重新建回来

另一个问题是同步期间删除子目录。发送端可能还拿着旧清单反复尝试已经不存在的文件；接收端也可能把目录重新创建出来，让用户刚做的删除看起来没有生效。

现在扫描会区分“文件确实消失”和“暂时被占用”。读取期间内容发生变化，或遇到文件共享冲突，会把路径放回待核对范围；如果整个同步根目录不可用，则报告错误，不把它解释成用户删除了全部文件。本机空目录也单独参与文件浏览，避免界面把“没有文件”显示成“目录不存在”。

图 5：目录删除与任务状态

接收任务会记住开始时仍然存在的父目录。这个父目录中途消失时，停止旧文件写入，并在索引中登记删除状态。后续请求还会比较删除记录和传入版本，拒绝旧修订重建目录，同时允许真正的新内容在重新核对后继续同步。

这里既要防止旧文件复活，也不能把一个路径永远封死。回归用例因此会继续在同一位置创建新文件，确认它还能同步，而不是只检查旧任务是否报错。实现与用例见 SyncEngine.cs、native-directory-races.test.cs。

3. 暂停要能中断扫描，也要能中断网络等待

只在任务启动前检查一次暂停开关，正在计算大文件哈希、等待网络响应的任务仍然会继续运行，界面上的“已暂停”就和实际状态脱节了。

现在扫描和哈希读取之间会检查取消状态，网络请求也有独立的取消检查，必要时调用 HttpWebRequest.Abort() 打断阻塞的等待。暂停状态保存在配置中，重启后仍然有效；恢复同步后按当前状态重新核对，旧任务不会因为按钮重新开启就继续获得写入许可。检查间隔并不等于固定的响应时间，磁盘与系统调用仍会影响实际停下来的速度。

4. 同步记录要说明实际改变了什么

“核对了多少文件”和“同步了多少内容”需要分开记。一次没有变化的核对，传输文件数和内容总量应该是零，不能因为遍历了整个目录，就给出一个很大的同步数字。

新版在两端记录本轮范围、耗时、文件数与内容大小，并分别统计发送、接收、删除、核对及未完成项。这里的内容大小是完成同步文件的逻辑大小，不是包含协议、重试开销的网卡流量。

文件动态带上来源电脑、操作和相对路径。整目录新增或删除时合并展示，单个文件修改仍单独记录，避免几百条子文件事件淹没真正需要看的变化。结构化详情会保存到磁盘，重启后仍能查看；导出诊断时再移除设备名和文件细节。实现见 ActivityEvents.cs。
