Python 闭包与装饰器：状态捕获与函数包装

发表于2026-05-29|更新于2026-11-16|Python 技术笔记进阶编程与工程基础
|总字数:1.3k|阅读时长:5分钟|浏览量:

想给几个函数增加耗时记录，最直接的办法是在每个函数前后插入计时代码。但重复插入很快会出现差异：有的忘记记录失败，有的遗漏返回值，有的只支持固定参数。

装饰器适合集中这层重复工作。理解它时，重点是包装前后还应保留哪些行为。下面从闭包开始，写一个可以独立运行的计时例子，使用 Python 3.10 及以上版本。

闭包的状态捕获与名称绑定

make_counter 已经返回，increment 仍然能访问它所引用的 count。两次调用 make_counter 形成不同的状态，因此 second 不会接着 first 的结果计数。

这里使用 nonlocal，是因为 count += 1 会对外层名称重新赋值。只是读取外层变量，或者修改一个已捕获列表的内容，并不因为“位于闭包中”就必须写 nonlocal。名称绑定规则可对照 Python 执行模型。

装饰器中保存的状态可以很简单：就是被包装的那个函数。

装饰器的接口契约

对于一个同步计时装饰器，本文采用以下约定：

  1. 原函数接收的参数，应原样转交。
  2. 原函数的返回值，应原样返回。
  3. 原函数抛出的异常，不由计时层改成默认值。
  4. 无论成功还是失败，都记录这次调用的耗时。
  5. 日志和调试工具仍能看到原函数名称。

这些约定比 @ 的语法更重要。一个只打印“开始、结束”却没有 return 的包装函数，会悄悄改变调用者拿到的结果。

同步计时装饰器的实现

终端会得到结果 2 和函数名 count_events，同时输出一条耗时日志。具体时间随运行环境变化，不应把某一次打印值当作性能结论。

@timed 对应于先定义函数，再执行 count_events = timed(count_events)。这里的装饰发生在函数定义阶段，wrapper 中的计时则发生在每次调用时。

参数转发、异常传播与元信息保留

*args 和 **kwargs 负责接收不同形式的实参，再交给原函数。它们不负责业务校验；原函数要求的关键字参数仍然要由调用者提供。

return func(...) 保留返回值。遗漏 return 后，即使业务函数计算正确，调用者得到的也会是 None。

finally 让失败调用同样经过计时记录。这里没有捕获业务异常；它会继续向上传播。日志设施自身如果也会抛错，则还需要另行约定日志失败的处理，避免让记录逻辑掩盖业务异常。

@wraps(func) 复制名称、文档等元信息，并提供 __wrapped__ 指向原函数。它不把包装函数变成原来的实现，也不自动解决类型检查问题。其具体行为见 functools.wraps。

计时范围与异步调用限制

perf_counter() 适合测量经过时间，两次读取之差才有意义。它测到的区间包括等待和调度时间，不等同于 CPU 执行时间。计时工具的区别见 Python time 文档。

这个装饰器也有明确的适用范围：

  • 装饰普通同步函数时，测量覆盖从进入业务调用到返回或抛错。
  • 装饰生成器函数时，调用通常只创建生成器，迭代过程发生在之后。
  • 装饰 async def 时，调用通常只创建协程对象。要计入异步执行过程，需要在异步包装器中 await 原调用。

因此，在生成器和异步函数上复用这个实现，可能得到看似正常、含义却错误的时间。判断测量是否有效，应先问真正的工作发生在哪个阶段。

包装函数的行为验证

成功结果之外，还应检查：

  • 传入关键字参数，调用是否正常；
  • 业务函数抛错，调用者是否仍能观察到原异常；
  • __name__ 是否保留；
  • 两个独立闭包是否各自维护状态。

如果包装层开始修改返回值、吞掉异常、重试请求，它就承担了新的业务语义，需要重新定义测试和适用范围。不要因为这些操作都能写进一个 wrapper，就把它们混在同一层里。

如果被包装的函数还涉及并发或网络 I/O，除了调用接口，还要检查任务何时结束、失败如何传递。相关例子见 线程与任务协作、Socket 消息边界。
