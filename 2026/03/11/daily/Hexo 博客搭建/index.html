Hexo 博客维护：配置管理、主题定制与部署流程

发表于2026-03-11|更新于2026-11-16|博客搭建
|总字数:2.3k|阅读时长:8分钟|浏览量:

博客搭好以后，真正反复发生的事情是写文章、调整页面、排查样式和确认发布结果。遇到“页面没变化”时，重新安装一遍依赖通常不是最有效的第一步。

这个站点使用 Hexo、Butterfly 和 GitHub Pages。下面按当前仓库的组织方式，梳理从源文件到线上页面的过程。涉及界面定制的部分，以这个站点实际调整过的模板和样式为例；部署步骤描述配置和检查方法，不把本地构建成功写成线上发布成功。

一、内容、构建与发布的分层模型

文章内容不对，先看 Markdown 和生成后的 HTML。DOM 结构不对，查模板。颜色被覆盖，查 CSS 的来源和优先级。远程仓库没有更新，再检查推送和认证。

这些检查对应不同层次。浏览器刷新不会重新读取服务进程尚未加载的配置，hexo clean 也不能修复 GitHub 仓库的权限问题。

二、仓库结构与配置优先级

public/ 是生成产物，不是内容的唯一来源。直接修改其中的 HTML 或 CSS，下一次生成时就可能被覆盖。

文章配图放在 博客笔记/img/ 中与笔记同名的目录，例如 数据容器.md 对应 img/数据容器/。原稿使用相对图片路径，方便 Obsidian 显示；构建时自动转换成站点的 /img/笔记名/文件名 地址。站点固定资源保留在 hexo/source/img/system/。没有配图的文章不必创建空目录，post_asset_folder 保持 false。

hexo/scripts/note-source.js 在初始化时将博客原稿和站点资源合成为 .generated-source/，预览时监听这两个来源的变化。只维护原稿，不修改生成副本；私人笔记不会进入构建输入。

本仓库目前直接维护主题目录中的配置和模板。Hexo 也支持根目录的 _config.butterfly.yml，配置优先级为：站点中的 theme_config、独立主题配置文件、主题自身的配置文件。迁移时应合并并检查配置，避免同一项散落多处。Hexo 配置文档说明了这些来源。

独立配置文件只能隔离配置覆盖，不能自动保护已经修改过的模板。这个站点的模板属于自维护部分，升级主题时仍然需要比较差异。

四、主题模板与样式覆盖

这个博客的文章列表改成了“日期与标签、标题、摘要”的顺序。仅靠 CSS 调换视觉位置容易留下不合适的文档顺序，因此对应调整放在 indexPostUI.pug 中；间距、字体和明暗配色则放在 custom.css。

相同原则也用于侧栏：完整照片、个人信息、分类和项目入口由模板组织。照片按原始宽高比显示，避免固定高度配合 object-fit: cover 把内容裁掉。

配色用变量集中维护，再接入主题已经提供的变量。这样正文、搜索和代码块可以共享主题状态，而不必为每个段落追加一组夜间覆盖规则。

排查这类问题时，浏览器开发者工具里的“计算样式”比继续增加 !important 更有帮助。先找到最终生效的声明，再决定应该删除重复规则、调整变量，还是精确覆盖组件。

五、PJAX 导航与静态资源加载

本站的 RSS 是 /feed.xml。文件正常返回，并不能保证点击页脚链接就会打开它：无刷新导航原先也尝试接管这类链接，但 RSS 不是它预期的 HTML 页面。

处理方式是给 RSS 保留普通链接行为，并排除 mailto:、下载和明确声明不参与 PJAX 的链接。导航优化应服务于页面切换，不应改变文件与外部协议的原本语义。

第三方 CDN 则属于资源可用性问题。这个站点把影响页面切换的 PJAX 同版本脚本保存到本地，并保留许可证。不是所有依赖都需要一并搬入仓库；优先判断失败会影响整页操作，还是只影响某个可延后加载的功能。

七、页面更新异常的排查流程

我会先确认源文件和目标页面是否对应，再看生成产物，最后查服务与浏览器：

  1. 修改是否写在真正生效的配置、模板或 CSS 中；
  2. public/ 对应页面是否包含新内容；
  3. 当前服务是否来自预期目录、是否已经加载新配置；
  4. 浏览器是否仍在使用缓存资源；
  5. 若是线上页面，发布分支和 Pages 任务是否实际完成。

hexo init 失败时也应区分 Git 拉取 starter 与包管理器下载依赖。更换 npm registry 只影响相应的包下载，不能直接解决 GitHub 克隆超时。

维护静态博客不必积累一长串固定重试命令。保留清楚的源文件边界、可重复的构建步骤，以及每一层的检查入口，下一次出现问题时才能缩小范围。
