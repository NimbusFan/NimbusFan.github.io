DeepSeek 接入 QQ：基于 AstrBot 的私聊机器人部署与调试

发表于2026-11-11|更新于2026-11-16|技术实践
|总字数:7.2k|阅读时长:26分钟|浏览量:

最近刷到不少网友把deepseek接入了QQ，评论区中某些大肥鱼展现出来的效果不亚于流浪地球2图恒宇手中的丫丫。于是心血来潮下在自己电脑上部署了一个。（ps：我只想给她完整的一生）

本文以 Windows 10/11 x64、本机运行 AstrBot、DeepSeek 官方 API、QQ 私聊为范围，先完成纯文本对话，再讨论人格、上下文和群聊扩展。

要实现这种体验，需要分别解决三个问题：QQ 如何把消息交出来，程序如何组织对话，模型如何生成回复。把这三层拆开，部署和排错都会清楚得多。

版本说明 · 2026-11-16：原先常见的 NapCat 下载路径已经发生变化。核对时，NapCat 上游仓库仅保留结束说明，原文档站返回 404。因此，新部署以当前可用的 QQ 官方机器人方案为主；已有 NapCat 的连接配置保留在文末。归档副本与上游正式发行版会明确区分。

接入方案与消息链路

官方机器人与普通 QQ 账号

两条路径都能提供 QQ 对话入口，但账号身份和维护方式不同。

路径 QQ 中的身份 接入方式 本文安排
QQ 官方机器人 独立的机器人身份，可进入消息列表单聊 AstrBot 连接 QQ 开放平台 新部署主线
NapCat + OneBot v11 登录一个普通 QQ 账号，由程序收发消息 NapCat 连接 AstrBot 已有部署的补充说明

官方机器人的效果是“像联系好友一样打开窗口聊天”，账号本身仍是机器人。创建它使用的个人 QQ 是管理账号，不会因此被交给 AstrBot 登录。当前官方接入入口支持快速创建和扫码绑定，具体可用场景由平台授权决定。腾讯官方接入说明

三层职责

QQ 平台负责消息通道，AstrBot 负责对话编排，DeepSeek 负责模型推理。本地电脑不运行模型权重，因此这套 API 方案不要求独立显卡；电脑需要保持联网，并持续运行 AstrBot。

排错也沿着这条链路进行：收到 QQ 事件、触发 AI、调用模型、发送回复，是四个独立的检查点。某一层“连接成功”，并不代表整条链路已经通过。

软件、账号与下载入口

主线需要 AstrBot Launcher、可用的 QQ 账号，以及 DeepSeek API Key。Python 运行环境交给启动器管理，不必先把 Python、Docker 和其他框架全部装一遍。

AstrBot 的安装与初始配置

启动器安装与实例创建

安装 Launcher 后，创建一个 AstrBot 实例，选择要部署的稳定版本，按界面提示下载运行环境、安装依赖并启动。启动器提供独立运行环境和实例管理，后续启停、升级及备份尽量通过同一个入口完成。Launcher 项目说明

可以使用容易辨认的实例名，例如 qq-deepseek。目录选普通用户可写的位置，例如 D:\Apps\AstrBot；使用短路径有利于排查路径问题，但“路径包含中文就一定无法运行”并不是通用结论。

首次启动需要下载依赖。若中途失败，先查看日志中失败的是运行环境、软件包还是 AstrBot 本身，处理对应下载源或网络问题，再重试。反复重装整个软件通常不能解释失败原因。

指定实际生效的配置文件

添加提供商只是注册一个可用模型，QQ 会话还需要选用它。在「配置文件」中选择准备分配给 QQ 机器人的配置，确认：

  1. 使用 AstrBot 内置 AI，并开启 AI 对话。
  2. 在「AI → 模型」中，将对话模型设为刚添加的 DeepSeek。
  3. 在「平台与消息」中检查私聊触发方式，允许目标私聊触发回复；首轮测试先发送普通文本。
  4. 查看访问控制，确保测试账号未被白名单、黑名单或其他规则排除。
  5. 保存配置，并在机器人实例中确认使用的确实是这份配置文件。

初次验证时，先保持文本输入、单条文本回复，暂缓安装第三方插件、图片理解和复杂工具。这样一旦失败，仍然能判断是哪一层引入了问题。WebUI 配置说明

QQ 官方机器人的创建与绑定

扫码接入

当前 AstrBot 官方文档提供了扫码创建流程：

  1. 在 WebUI 中打开「机器人」，点击「创建机器人」。
  2. 选择 QQ 官方机器人（WebSocket），创建方式选「扫码一键创建」。
  3. 用手机 QQ 扫描页面中的二维码，核对授权信息并确认。
  4. 等待绑定完成，确认 AppID、AppSecret 已由程序填入，启用并保存实例。

此处选择的是 QQ 官方适配器，不是 OneBot v11。它不需要 NapCat，也不使用 6199/ws 这个本地地址。AstrBot QQ WebSocket 接入说明

若所用版本没有扫码入口，先核对核心版本和对应文档；也可以在 QQ 开放平台创建机器人，再把该机器人的 AppID、AppSecret 填入官方 WebSocket 适配器。管理账号的 QQ 密码和 DeepSeek API Key 都不能替代这两个字段。

官方接口通过平台颁发的凭据鉴权。不要从旧教程中复制已经弃用的固定 Token 鉴权写法，访问令牌的获取和刷新交由当前适配器处理。QQ 官方接入票据说明

消息列表单聊

确认机器人配置中的 “启用消息列表单聊”（enable_group_c2c）处于开启状态。频道私信是另一种消息场景，不能拿“频道里能聊天”代替消息列表私聊验证。

在 QQ 开放平台打开该机器人的「扫码聊天」或添加入口，用手机 QQ 扫码，确认后打开对话窗口。平台采用测试范围或沙箱时，还要把测试 QQ 加入允许的使用范围；能创建机器人，并不意味着所有账号立即都能与它对话。

完成后，在 QQ 的消息列表中应能找到这个机器人。它的名字可以设置成“大肥鱼”，但昵称设置与消息连接是独立的操作。

如果平台提示需要配置 IP 白名单，填写运行 AstrBot 这台机器的出口公网 IP，并留意网络切换后的变化。这与开放本机管理端口不是一回事。

首轮验证

按顺序进行三次测试，每次都等待上一条回复完成：

测试消息 观察目标
只回复：QQ 连接正常。 一次完整收发，QQ 中实际出现回复
接下来请把本次对话里的项目代号记作青石。，随后问 项目代号是什么？ 当前会话上下文是否连续
使用另一个已获授权的测试账号发送 我们刚才确定的项目代号是什么？ 第二个账号是否错误继承了第一个账号的内容

第三项是会话隔离的抽查，单次回答不能证明所有隔离逻辑正确。还应检查实际会话标识及配置，避免不同用户共用同一段历史。

在 AstrBot 的「数据与日志」中，分别确认事件接收、模型请求与发送结果。模型生成了文字只是中间状态，QQ 聊天窗口收到消息，才算本轮接入完成。

人格、上下文与回复策略

简短且一致的人格设定

“像一个能交流的对象”主要依赖稳定的表达方式和连续的上下文。人格提示词先写清身份、语气和边界即可，过多的口头禅、禁词和情绪等级反而容易互相冲突。

修改后先保存，再新建测试对话，排除旧历史对语气的影响。是否需要重载或重启，取决于所用版本与修改对象，不能统一写成“改人格必须重启”。AstrBot 的人格管理接口本身包含缓存刷新机制。人格管理说明

会话上下文与长期记忆

当前对话中的前文、保存到磁盘的聊天记录、专门提取的长期记忆，是三种不同的数据。保存了聊天记录，不代表每轮都把全部记录送入模型；重启程序后是否能接续，也取决于会话恢复与存储配置。

私聊至少应按机器人实例与对端用户隔离；群聊则需要明确选择“全群共享”还是“群内按人隔离”。例如，同一个用户在私人对话中说过的话，不应因为用户 ID 相同，就自动被带进群聊。

验证新人格时可以使用 /new 创建新对话，保留旧对话供回看；/reset 用于清空当前对话上下文。指令的权限与具体行为受版本、会话类型和指令设置影响，它们也不等于删除插件中的长期记忆。内置指令说明

输出长度与消息分段

提示词中的“一到三句”是风格要求，不是长度保证。max_tokens 限制的是模型输出 token 数，也不等于中文字符数。需要严格控制发送长度时，应由程序在发送前处理。

但技术对话不适合简单地“超过 60 字就截断”：这可能截掉结论、命令参数或代码围栏。更合理的策略是按消息用途区分：闲聊保持短回复，解释型内容保留必要结构，确实超过平台限制时再分段。

首次配置先关闭人为打字延迟和复杂分段。稳定后一次只增加一种行为，观察消息数量与发送结果。无节制拆成多条消息既增加打扰，也让超时和重试更难判断。

群聊扩展

私聊稳定后再把机器人加入允许的群聊，先采用“明确 @ 才回复”的触发规则。群里存在两道判断：平台是否把事件发给程序，以及 AstrBot 是否决定触发 AI，二者需要分别核对。

普通文本 @大肥鱼 与 QQ 原生提及消息不是同一种消息结构。手打名字的消息可能已经到达 AstrBot，只是没有满足提及触发条件，不能据此写成“程序收不到”。

如果以后需要群上下文，再按平台当前支持范围申请或开启消息权限。让机器人接收更多消息，与让它回复每一条消息，也应分别配置。

按消息链路定位故障

QQ 事件与 AI 触发

现象 优先检查
扫码绑定后无法找到聊天入口 是否绑定了正确机器人、使用了平台提供的聊天二维码、测试账号是否获授权
QQ 发出消息，AstrBot 没有对应事件 官方适配器是否在线、消息列表单聊是否启用、使用范围和平台凭据是否正确
日志有事件，但没有模型请求 私聊触发、访问控制、AI 开关、配置文件路由及插件拦截
只有某个账号不回复 该账号的使用权限、会话配置覆盖和访问控制
一条消息收到两份相同回复 是否同时运行了两个实例、重复接入同一个机器人，或存在重复处理插件

不要同时修改人格、模型参数和接入地址。选一条带有明确时间点的测试消息，沿日志检查它在哪一步停止，比一次改十个开关更容易得到结论。

DeepSeek 请求失败

HTTP 状态或现象 检查方向
400 / 422 请求体、模型 ID、消息格式和额外参数；以响应正文指出的字段为准
401 Key 是否有效，是否复制了空格、漏字符或填成其他平台密钥
402 API 账户余额是否充足
429 调用频率或并发是否超限，是否因重试产生了额外请求
500 / 503 服务端错误或繁忙，等待后有限重试
连接超时 在运行 AstrBot 的环境中检查 DNS、代理和 API 连通性，区分连接阶段与推理等待

错误状态应与响应正文一起看。出现 401 或余额不足时，反复重连 QQ 无法解决；遇到限流，也不应无限循环重试。DeepSeek 官方错误码

已生成回复但 QQ 未收到

此时优先看 QQ 发送接口的返回结果、适配器错误和消息结构，暂时不必继续改模型。

先用短纯文本复现，再分别测试链接、代码、图片或其他消息类型。QQ 官方接口对不同消息场景和内容有自己的发送要求；例如，包含链接的内容可能需要平台侧配置，不能仅凭模型测试成功就推断任意内容都能发出。腾讯官方消息发送说明

同样，单次“消息体无法解析”也不能推出“QQ 一律不允许纯表情”。应保存脱敏后的失败载荷，核对消息类型、字段和协议端版本，再与能成功发送的最小消息比较。

反向 WebSocket 的方向

NapCat 是 OneBot 协议实现端，AstrBot 是应用端。使用反向 WebSocket 时，由 AstrBot 监听，NapCat 主动连接。一个连接同时承载消息事件和 API 调用，回复仍经 NapCat 发回 QQ。

先在 AstrBot 的「机器人 → 创建机器人」中选择 OneBot v11，启用实例。以下取值只用于两个程序都原生运行在同一台 Windows 电脑的情况。

AstrBot 配置项 取值
实例 ID 例如 qq-napcat
反向 WebSocket 主机地址 127.0.0.1
反向 WebSocket 端口 6199
反向 WebSocket Token 自行生成的一段随机值

再从 NapCat 启动日志打开实际 WebUI，默认端口通常为 6099，登录 token 以当前日志或当前配置为准。在「网络配置」新增 WebSocket 客户端：

NapCat 配置项 取值
URL ws://127.0.0.1:6199/ws
消息格式 array
Token 与 AstrBot 的反向 WebSocket Token 完全一致
启用 开启并保存

6185 是 AstrBot 管理页面，6099 是 NapCat 管理页面，6199 才是这里的 OneBot 连接端口。WebUI 登录 token、OneBot 连接 token 和 DeepSeek API Key 是三组不同凭据。

保存后查看两端日志，确认适配器完成连接，再用自己的 QQ 添加机器人所登录的账号为好友，按账号设置完成好友请求确认，发送私聊测试。AstrBot OneBot v11 接入说明

端口与运行环境

可以在 PowerShell 中查看监听和已建立的 TCP 连接：

Listen 说明端口正在监听；Established 说明某条 TCP 连接已建立。它们都不能单独证明 WebSocket 鉴权、OneBot 事件、模型调用和 QQ 回复已经成功，仍须结合日志和实际消息判断。

运行方式 NapCat 中的连接地址原则
两者都在同一台电脑原生运行 使用 127.0.0.1:6199
两者在同一个 Docker 网络的不同容器中 使用 AstrBot 的容器服务名；AstrBot 需监听容器可达地址
NapCat 在容器中，AstrBot 在宿主机 使用容器可达的宿主机地址，同时调整 AstrBot 监听与防火墙

127.0.0.1 指向当前进程所在的网络环境。把这条本机地址原样搬进另一台机器或另一个容器，是常见的连接错误。0.0.0.0 则是监听所有网卡的绑定地址，不是应该填给客户端的目标地址。

换 QQ 账号后，还要重新检查该账号实际加载的 OneBot 配置。QQ 在线、NapCat 运行、AstrBot 运行，不能代替二者已经连接的证据。

运行成本与维护

Token 与响应时间

一次 API 请求的输入通常包含人格、当前问题、历史消息，有工具时还可能包含工具说明和结果。聊天越长，下一轮需要携带的历史往往越多，所以不能按“每条 QQ 消息固定多少钱”估算。

将 token 数量按官方价格的计量单位换算；若使用峰谷价格或额外的搜索、文件、语音服务，也要分别计入。先观察几天实际用量，再决定上下文长度和预算，不给出缺少使用条件的“每天几毛钱”。DeepSeek 模型与计费说明

回复慢也要拆开测量：QQ 事件到达、应用排队、模型请求、平台发送分别耗时多少。优先处理其中占比最大的部分。把输出拆成三条、再人为延迟发送，只会改变聊天节奏，不会让推理本身更快。

数据与升级

使用可视化 Launcher 的实例，数据位于用户目录下的 .astrbot_launcher 体系中，具体实例路径从启动器确认。备份应包含配置、人格、会话数据库，以及确实安装过的插件和插件数据；QQ 平台凭据与模型密钥也要随备份妥善保管。数据目录说明

优先使用启动器的备份和停止功能。手动复制数据库前先正常停止实例，避免只复制主数据库文件却漏掉仍在写入的数据。升级一次只变动一个组件，并记录升级前后的版本，便于回退。

手动改 JSON 时，明确使用 UTF-8、先做备份，再校验 JSON 语法和中文内容。ConvertTo-Json 本身并不必然破坏中文；读取编码和写入编码不匹配，才是需要检查的环节。文件已经损坏时，优先恢复已知正常的版本，不要反复盲目转码。

在线状态与功能扩展

电脑关机、休眠、断网或 AstrBot 退出，都会影响本机机器人的在线服务。合上笔记本后是否继续运行，要结合系统电源设置确认。关闭管理页面与停止后台进程也不是一回事。

需要常驻时，再考虑开机启动和进程恢复；定期检查 QQ 连接状态、模型失败率与余额即可。图片、搜索、语音、记忆和主动消息，都应在纯文本链路稳定后单独接入和验证。

新增插件时，记录准确的仓库地址、版本和权限需求。只有“记忆插件”“表情插件”这样的功能描述，没有代码或可安装的项目，就不能算可复现的部署步骤。普通聊天也没有必要默认开放本机文件、终端或其他高权限工具。

部署验收

完成部署后，按下面几项检查实际行为：

  • 已从可信发布入口安装软件，并记录 Launcher 与 AstrBot 核心版本。
  • DeepSeek 独立测试能够返回正文，并能查看调用用量。
  • QQ 中能找到目标机器人，私聊消息完成实际往返。
  • QQ 会话使用的模型、人格和配置文件与预期一致。
  • 同一会话能接续前文，不同测试账号没有意外共享上下文。
  • 日志能区分“未收到事件”“未触发 AI”“模型失败”和“发送失败”。
  • 正常停止并重新启动后，配置仍然存在，连接和私聊能够恢复。

做到这里，才得到了一套可以继续维护的 QQ 对话入口。人格和插件可以慢慢调整；连接状态、会话边界以及失败原因，应当从第一版就能够解释。
