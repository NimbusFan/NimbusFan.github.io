Python 线程池：任务调度、异常传播与资源回收

这个输入示例假定路径列表中没有重复任务。结果用路径字符串作键，避免不同目录中的同名文件仅因文件名相同就被合并；若同一路径需要处理多次，应另设任务标识。

Future 的结果读取与异常传播

submit 返回的 Future 代表这次任务。业务函数中的异常会在读取 future.result() 时重新抛出，而不是因为工作线程已经结束就自动成为主线程中的处理结果。concurrent.futures 文档说明了这些行为。

本例只收集 I/O 和解码失败，让其他编程错误继续暴露。若把所有 Exception 都转换成空结果，接口使用错误也可能被误判为“文件里没有记录”。

“已经收集完任务”和“所有任务都成功”是两个不同结论。这里分别返回结果和错误，调用者仍需决定：允许部分结果，还是要求整批重试。

线程池关闭、超时与任务取消

with ThreadPoolExecutor(...) 退出时会等待相关任务完成。它让关闭过程明确，也意味着其中一个任务永久阻塞时，主流程并不会因为离开某段代码就立刻结束。

future.result(timeout=...) 限制的是等待结果的时长，不会自动杀掉正在运行的任务；cancel() 也不能任意停止已经开始运行的线程。

需要可控退出时，应在真正的阻塞操作处设置合适的超时，或者让任务在安全检查点响应停止信号。任务停止后，文件、连接等资源仍需要正常释放。

工作线程数、在途任务与背压

max_workers=3 限制同时工作的线程数。示例却在开始时就提交了全部路径，等待中的任务数量仍然与输入数量有关。

对于有限的小批次，这样组织很直接。面对持续产生的数据，应控制在途任务数量，或使用具有容量限制的队列形成背压。queue.Queue(maxsize=...) 提供线程间同步；使用其任务完成机制时，每次 get 对应的 task_done 也要覆盖异常和退出路径。相关约定见 queue 文档。

此外，队列保护的是入队、出队等操作，不会自动保护被传入对象内部所有后续修改。把一个可变对象交给多个线程之前，仍然要明确所有权。

I/O 并发与 GIL 的适用边界

I/O 等待较多、任务之间相对独立时，可以考虑这种组织方式。对受 GIL 限制的常规 CPython 纯 Python 计算，不能仅凭增加线程数就推断会获得多核加速；扩展模块和解释器构建方式也会影响结果。

先定义正确的结果与退出行为，再针对代表性负载比较吞吐、延迟和资源占用。本文没有将微小文件上的运行时间作为并发性能证据。
