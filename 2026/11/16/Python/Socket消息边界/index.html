TCP 消息边界：长度前缀协议与 Socket 读写

发表于2026-11-16|更新于2026-11-19|Python 技术笔记进阶编程与工程基础
|总字数:1.2k|阅读时长:4分钟|浏览量:

最初的 Socket 示例通常是 send 发送一段文字，recv(1024) 接收后打印。在很小的本地实验里，它可能恰好按预期工作，但代码中没有任何机制说明“一条消息到哪里结束”。

TCP 提供字节流，不保留应用程序每次发送的消息边界。一次发送的内容可能需要多次读取，多次发送的内容也可能出现在一次读取中。因此，接收缓冲区大小不能代替协议设计。这个区别见 Python Socket HOWTO。

一、长度前缀协议与消息约束

长度计算的是编码后的字节数，不是字符串字符数。再约定单条消息最大为 64 KiB，避免对端声明一个过大的长度后让接收方无限等待或分配大量内存。

空消息是合法字符串 ""。连接在两条消息之间正常结束时返回 None；如果长度头或正文只收到一部分就断开，则抛出异常。这些情况必须能够区分。

三、部分读写与字节流重组

recv(size) 给出的是本次最多接收的字节数，没有承诺一次填满请求长度。头部第一次可能只收到 1 字节，正文也可能分成多段，所以二者都需要补齐。

sendall 帮助处理发送过程中只能写出一部分数据的情况；它不能证明对端应用已经处理了消息。需要确认处理成功时，应在应用协议中增加响应或确认机制。socket 文档区分了这些接口的职责。

这里先收齐正文，再执行 UTF-8 解码。一个字符的多个字节可能被分到不同读取中，直接对每次 recv 的结果单独 decode，可能在字符边界处失败。

四、协议异常与连接状态恢复

长度非法、UTF-8 解码失败、消息中途断开，都不是收到了一条有效消息。调用者需要关闭连接或执行明确的协议恢复流程，不能简单捕获异常后继续读下一条。

例如，读取正文超时后，这个实现中的局部缓冲内容不会作为解析状态保留。重新调用 recv_text 会把后续字节当作新头部，可能进一步错位。实际服务若要支持中断后继续解析，需要有跨调用保存的状态机。

这个例子也没有实现连接认证、加密、并发会话和应用级重试。长度前缀只解决消息划分及基本长度约束，不能将一个可运行的本地示例当作完整服务端。

五、分段接收与异常路径验证

除了正常收发，至少检查：

  • 连续发送两条消息，是否能分别读取；
  • 一个消息按多个字节片段到达，是否能补齐；
  • 空消息与连接结束是否能区分；
  • 头部声明超长、正文被截断时，是否明确失败；
  • 中文内容是否按编码后的字节长度处理。

这些检查不依赖真实摄像头或远程服务器，可以先在本地完成。接口层的协议正确性与现场网络条件，应分别验证。
