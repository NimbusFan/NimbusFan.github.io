Git 版本管理：提交模型、分支策略与变更撤销

发表于2026-06-13|更新于2026-11-16|Git
|总字数:7.6k|阅读时长:28分钟|浏览量:

处理 Git 问题之前，先确认三个状态：修改还在工作区，已经放进暂存区，还是已经成为其他人可能依赖的提交。状态不同，同一个“撤销”需求对应的命令也不同。

这篇笔记围绕一次功能分支的生命周期展开。示例假定默认分支叫 main、远程名为 origin，尖括号中的提交标识需要替换为实际值。示例命令用于说明工作流，不会自动适用于所有仓库的分支规范。

工作区、暂存区与提交快照

工作区是当前文件，暂存区描述准备提交的内容，提交对象保存一次版本快照及其历史关系。

git diff 默认比较工作区与暂存区，git diff --cached 比较暂存区与当前提交。新建但尚未跟踪的文件不会因为出现在工作目录中，就自动进入这两个 diff 的内容。

最容易混淆的情况是：暂存了一个文件，又继续修改它。此时工作区和暂存区保存的是不同版本，直接 commit 提交的仍然是暂存内容。

因此，提交前应审查 git diff --cached，不能仅凭编辑器里最终显示的代码判断将要提交什么。

提交粒度与差异审查

假设同一轮工作修改了过滤逻辑、更新说明，又调整了编辑器配置。如果把它们放进同一提交，审查者需要同时理解三件事，之后撤销功能时还会牵连无关内容。

add -p 允许按差异块选择内容；新建文件等情况仍需按文件暂存。划分提交的标准是逻辑是否完整，不是机械地做到“一次只改一个文件”。

一个函数签名的修改和全部调用点，可能应在同一提交中；同一个文件中两项互不依赖的修改，也可能应拆开。拆分之后还要检查中间提交是否具备有意义的状态。

fetch 更新远程跟踪引用，不直接修改当前工作文件。随后显式进行快进合并，比在不了解策略时依赖一次 pull 更容易判断发生了什么。

--ff-only 的意义是：如果本地 main 与远程已经分叉，就停止，先检查历史。它不是“忽略本地提交并强制同步”。

Restore、Reset 与 Revert 的适用范围

下面几个操作经常被笼统叫作“回退”，实际上作用不同。

需求 操作 需要理解的后果
取消暂存，但保留文件修改 git restore --staged path/to/file 修改仍在工作区
丢弃某文件的未暂存修改 git restore --worktree path/to/file 默认恢复为暂存区版本，未必是 HEAD
撤掉最近一次本地提交，保留暂存内容 git reset --soft HEAD~1 分支指针后退，暂存区与工作区保留
撤掉最近一次本地提交，保留工作文件 git reset --mixed HEAD~1 暂存区回到目标提交，修改留在工作区
抵消一个已经共享的提交 git revert <commit> 创建新的反向提交，保留原历史

restore 针对文件内容的来源，reset 可以改变分支和索引状态，revert 则通过新提交抵消改动。详细区别可以分别查 restore、reset 和 revert。

reset --hard 还会将工作区中受跟踪文件的内容恢复到目标状态，可能丢弃尚未提交的修改。它不应成为“出了问题就试一下”的默认动作。准备改写本地提交前，可以先创建一个指向当前提交的备份分支：

备份分支保存的是提交位置，不包含未提交的文件改动。它也不能代替对工作区状态的检查。

Stash 的保存范围与恢复行为

-u 将未跟踪文件一并纳入；被忽略文件不在这个范围内。apply 在恢复时保留 stash 条目，便于先检查，再决定是否删除对应条目。

恢复也可能冲突，尤其是基线已经改变时。stash 适合临时保存现场，不适合作为长期版本记录：它通常没有功能分支清晰的组织、审查和共享流程。

Reflog 与本地提交恢复

误移动分支后，可以先查看引用在本地的变更记录：

先建立救援分支，再检查代码，通常比再次盲目移动当前分支更容易保留判断空间。reflog 记录本地引用的变化，也有保留期限；它不保证恢复从未提交、从未保存进 Git 对象的任意文件内容。相关机制见 git-reflog。

如果变基后的分支确实需要覆盖自己的远程分支，--force-with-lease 能在引用检查上提供比无条件强推更严格的约束，但仍不保证业务上没有覆盖他人工作。尤其使用未显式指定预期提交的形式时，后台 fetch 也会影响远程跟踪引用。需要这种操作时，应先读清 git-push 的约束，并与协作者确认历史是否可以改写。

Git 命令速查清单

以下按任务分类查阅，表格中的命令是独立示例，不是从上到下执行的脚本。默认分支为 main、远程名为 origin；<commit>、<url>、<name> 等为占位符，执行前替换。src/filter.py、tmp/ 等路径同样应改成当前仓库中的实际路径。

引用表达式与路径参数

写法 含义
HEAD 当前检出的提交；在分支上时通常通过分支引用间接指向它
HEAD~1、HEAD~3 沿第一父提交链向前移动 1 次、3 次
HEAD^1、HEAD^2 当前提交的第一、第二父提交；第二父提交通常出现在合并提交中
main、origin/main 本地分支与本地保存的远程跟踪引用；后者不是实时查询服务器
<commit> 实际的提交哈希或其他能解析到提交的引用
-- src/filter.py 在这些示例中分隔提交／选项与路径，减少同名分支和文件引起的歧义

HEAD~2 与 HEAD^2 不同：前者沿第一父链走两步，后者选择当前提交的第二父提交。普通线性提交一般没有第二父提交。

路径含空格时加引号，例如 git diff -- "docs/Git notes.md"。PowerShell 中引用 stash@{0}、HEAD@{1} 时也建议使用单引号，避免花括号被 shell 解释。

身份配置与仓库创建

命令 用途与作用范围
git --version 查看当前 Git 版本，排查某个命令或选项是否受支持
git config --list --show-origin 查看有效配置及配置文件来源，排查全局与仓库配置的覆盖关系
git config --global user.name "<name>" 设置当前系统用户的默认提交署名
git config --global user.email "<email>" 设置默认提交邮箱；它属于提交元信息，不等于远程登录凭据
git config --local user.name "<name>" 仅为当前仓库覆盖提交署名，适合区分个人与工作项目
git config --local user.email "<email>" 仅为当前仓库覆盖提交邮箱
git init -b main 在当前目录初始化仓库，并指定初始分支名称；不会自动创建第一次提交
git clone <url> project 将远程仓库克隆到 project 目录，通常同时配置名为 origin 的远程

先用 --show-origin 确认生效来源，再决定修改哪一级配置。某个项目的身份信息不对时，不必直接改掉其他项目也会使用的全局配置。

工作区状态与差异检查

命令 比较对象或输出
git status 查看当前分支、暂存状态、未暂存修改、未跟踪文件及进行中的操作
git status -sb 简短状态加分支信息，适合开始工作与提交前快速检查
git diff 工作区相对于暂存区的变化，即尚未暂存的部分
git diff --cached 暂存区相对于 HEAD 的变化，即下一次普通提交准备写入的内容
git diff HEAD 当前工作区相对于 HEAD 的最终差异；不展示未跟踪文件内容
git diff --stat 以文件和增删行数概览未暂存差异
git diff --name-status 列出未暂存差异的文件名与变更类型，例如新增、修改、删除
git diff --cached --check 检查已暂存差异中的空白问题等，不等同于语法检查或测试
git diff -- src/filter.py 将未暂存差异限制在指定文件或目录

下面三种写法需要单独区分：

命令 含义
git diff main feat/frame-filter 比较两个分支尖端所指向的文件快照
git diff main..feat/frame-filter 在 diff 中也是比较两个端点；不是逐个展示区间中的提交
git diff main...feat/frame-filter 从两者的合并基点比较到功能分支，便于审查该分支一侧相对共同基线的改动

三点比较的两侧有方向：交换 main 和功能分支，比较目标就会改变。相关定义见 git-diff。

历史查询与代码追踪

命令 查询目的
git log --oneline --decorate --graph --all -n 30 用简短提交信息、引用名与图形查看最近的分支关系
git log -p -n 3 -- src/filter.py 查看影响指定文件的最近 3 个提交及补丁
git log --follow -- src/filter.py 追踪单个文件的历史，尝试跨越重命名继续查找
git show <commit> 查看提交说明和该提交引入的变化
git show <commit>:src/filter.py 查看某次提交中该文件的内容，不修改当前工作文件
git blame -L 20,60 -- src/filter.py 查询文件第 20 至 60 行最近对应的修改提交
git grep -n "camera_id" -- src/ 在工作区的已跟踪文件中搜索字符串，并显示行号
git log -S "camera_id" -- src/filter.py 查找改变该字符串出现次数的提交，适合追溯某段逻辑的引入或移除
git log -G "camera.*id" -- src/filter.py 查找增删行匹配正则表达式的提交

-S 关注字符串出现次数是否改变，-G 关注补丁中的增删行是否匹配；仅仅移动或重写一行时，二者可能给出不同结果。git-log 对这组查询选项有完整说明。

暂存与提交组织

命令 行为与注意点
git add -- src/filter.py 将指定文件此刻的内容加入暂存区；后续修改仍需再次暂存
git add -p -- src/filter.py 按差异块选择暂存内容，适合拆分同一文件中的不同改动
git add . 暂存当前目录及其子目录的新增、修改和删除；从子目录执行时不覆盖目录外的改动
git add -A 未给路径时，暂存整个仓库的新增、修改和删除
git add -u 未给路径时，暂存整个仓库中已跟踪文件的修改和删除，不自动纳入未跟踪文件
git commit -m "fix: validate camera id" 将暂存区形成一个新提交
git commit -am "fix: validate camera id" 自动暂存已跟踪文件的修改和删除后提交；不会自动加入未跟踪的新文件
git commit --amend --no-edit 用当前暂存区重建最近一次提交，保留提交说明，适合补齐尚未共享的提交
git commit --amend -m "fix: validate event records" 重建最近一次提交并修改说明；已经暂存的内容也会一并进入新提交

amend 生成新的提交对象，不是原地编辑旧提交。即使只是准备修改提交说明，也应先看 git diff --cached，确认没有夹带其他修改。提交选项见 git-commit。

分支创建、切换与清理

命令 用途与边界
git branch --show-current 查看当前分支名；处于 detached HEAD 时可能没有分支名输出
git branch -vv 查看本地分支、上游及领先／落后信息；这些信息基于本地引用
git branch -a 同时列出本地分支与远程跟踪分支
git switch main 切换到已有分支；会覆盖本地修改的情况通常会被拒绝
git switch -c feat/frame-filter 从当前提交创建并切换到新分支
git switch --track origin/feat/frame-filter 本地尚无同名分支时，从远程跟踪引用创建分支并设置上游
git switch - 返回上一次检出的位置
git switch --detach <commit> 检出某次提交进行检查，当前 HEAD 不附着在普通分支上
git branch -m feat/frame-filter-v2 重命名当前本地分支，不同步重命名远程分支
git branch --merged main 列出尖端提交已包含在本地 main 历史中的分支
git branch -d feat/frame-filter 在合并检查通过后删除本地分支；不能删除正在使用的分支
git branch -D feat/frame-filter 跳过合并检查删除本地分支引用；仍不能删除正在检出的分支，执行前确认独有提交另有保留

-d 检查的是该分支的上游；没有配置上游时，才使用 HEAD 作为合并关系的判断目标。因此，命令执行成功不等于“该功能已进入主分支”。分支清理前仍应查看 --merged main 或实际历史，参见 git-branch。

detached HEAD 状态下如果产生了需要保留的新提交，可以用 git switch -c debug/frame-filter 创建分支，使其获得明确的引用。

远程仓库与上游配置

命令 用途与影响
git remote -v 查看远程名称与抓取、推送地址
git remote add origin <url> 为当前仓库新增远程配置，不立即拉取或推送
git remote set-url origin <url> 修改远程地址，不迁移远程仓库中的内容
git fetch origin 抓取对象并更新远程跟踪引用，不直接合并进当前分支
git fetch --prune origin 同步并清理远程已不存在的跟踪引用，不删除同名本地分支
git branch --set-upstream-to=origin/feat/frame-filter 为当前分支设置已有的上游引用，影响状态比较及默认同步行为
git push -u origin feat/frame-filter 推送功能分支，成功后设置其上游
git push origin HEAD:feat/frame-filter 将当前提交推送到指定远程分支，明确源与目标
git push origin --delete feat/frame-filter 删除服务器上的分支；与删除本地分支是两件事

普通推送被拒绝时，先 fetch 并检查历史。可能是远程已有新提交，也可能是认证、权限或保护规则限制；不能把所有拒绝都解释成“需要强推”。

分支同步、合并与变基

命令 适用场景
git pull --ff-only 抓取后仅允许快进更新；本地与上游分叉时停止，适合保持主分支更新过程明确
git pull --rebase 抓取后以变基方式整合当前分支的本地提交；执行前确认历史可以改写
git merge --ff-only origin/main 不额外抓取，仅尝试将当前分支快进到本地保存的 origin/main
git merge origin/main 将远程跟踪引用合并进当前分支；可能快进，也可能生成合并提交
git merge --no-ff feat/frame-filter 将功能分支合并进当前分支，并保留显式合并节点
git rebase origin/main 将当前分支的提交重新应用到指定基线上，成功后提交标识通常改变
git rebase -i HEAD~3 交互整理指定基线之后的提交；在线性历史中对应最近三次提交，会重写历史

pull 会先抓取，而单独运行 merge、rebase 不会自动刷新 origin/main。后一组命令之前通常先执行 git fetch origin。

交互变基中的 pick 表示保留提交，reword 修改说明，edit 停下来修改提交，squash 合并并整理说明，fixup 合并改动并丢弃该条提交的说明，drop 移除提交。它们操作的是待重放的提交序列，不能只凭名字判断是否适用于已共享历史。

存在合并提交时，HEAD~3 沿第一父链选择基线，待重放集合可能多于三个提交，默认变基也可能改变合并结构。先查看提交图，再确定整理范围。完整规则见 git-rebase。

冲突检查与操作继续

命令 当前状态与作用
git status 先确认正在进行的是 merge、rebase 还是 cherry-pick，以及哪些文件尚未解决
git diff --name-only --diff-filter=U 只列出尚未完成合并的文件
git ls-files -u 查看索引中的未合并条目与阶段，适合进一步分析冲突
git add -- src/filter.py 编辑并确认结果后，将该文件标记为已解决；不会替代人工判断
git merge --continue merge 的冲突全部解决后完成当前合并
git merge --abort 放弃当前合并并尝试恢复开始前状态；开始前已有未提交修改时，恢复并非总能完整完成
git rebase --continue 解决当前补丁的冲突后继续重放，之后仍可能遇到新的冲突
git rebase --abort 放弃当前变基并回到开始前的分支位置
git rebase --skip 跳过正在重放的整个提交，不是仅忽略其中的冲突行

在 merge 与 rebase 中，ours、theirs 对应的上下文不同。尤其 rebase 会把上游作为重放基线，不能把“ours 永远是我原来的功能分支”作为规则。使用整文件选边之前，先确认每一侧实际包含什么。

文件恢复与提交撤销

命令 保留与丢弃的内容
git restore --staged -- src/filter.py 默认将该文件的索引状态恢复到 HEAD，取消暂存，保留工作文件
git restore --worktree -- src/filter.py 用暂存区版本覆盖工作文件，丢弃未暂存修改
git restore --source=HEAD --worktree -- src/filter.py 用最近提交版本覆盖工作文件；暂存区不变，因此工作文件可能与暂存区不同
git restore --source=<commit> --worktree -- src/filter.py 提取历史文件到工作区，不移动当前分支；会覆盖该文件的当前工作内容
git restore --source=HEAD --staged --worktree -- src/filter.py 同时恢复索引和工作文件到 HEAD，丢弃该文件尚未提交的改动
git reset --soft HEAD~1 撤掉最近一次本地提交，保留暂存区与工作区
git reset --mixed HEAD~1 撤掉最近一次本地提交，索引恢复到目标提交，工作文件保留
git reset --hard <commit> 将分支、索引和受影响的工作文件恢复到目标状态，可能丢失未提交改动
git revert <commit> 为普通提交生成反向提交，适合撤销已共享改动；也可能产生冲突

reset --hard 不是“只删除 Git 里的最后一次记录”：它会改写工作文件，也可能覆盖或移除妨碍检出的未跟踪路径。revert 若指向合并提交，还必须选择主线父提交；需要先分析历史，不宜随意补上一个 -m 1。

取消暂存与丢弃工作文件是不同操作，是否指定 --source 也会改变恢复来源。可分别核对 git-restore、git-reset、git-revert。

临时保存与恢复现场

命令 保存范围或恢复行为
git stash push -m "wip: frame filter" 保存已跟踪文件的工作区、索引修改，并恢复到 HEAD 状态；默认不包含未跟踪文件
git stash push -u -m "wip: frame filter" 额外保存并移走未跟踪文件，仍不包含忽略文件
git stash list 列出保存的条目，最新一项为 stash@{0}
git stash show -p --include-untracked 'stash@{0}' 检查该条目的补丁，包括已保存的未跟踪文件
git stash apply 'stash@{0}' 恢复条目并保留它，允许检查结果后再清理
git stash apply --index 'stash@{0}' 尝试连暂存状态一并恢复；存在冲突时可能失败
git stash pop 'stash@{0}' 恢复成功后删除条目；发生冲突时通常仍保留条目
git stash drop 'stash@{0}' 删除指定条目，执行前确认需要的内容已经保留

apply、pop 可能与当前工作发生冲突，不能视为无条件恢复。恢复后再次查看 status 与差异，再决定是否删除条目。--index 和条目保留规则见 git-stash。

指定提交的移植

命令 用途
git cherry-pick <commit> 将指定提交的改动应用到当前分支并生成新提交，常用于移植独立修复
git cherry-pick -n <commit> 应用改动到索引和工作区，暂不提交，便于检查或与其他改动一起组织
git cherry-pick --continue 解决并暂存冲突后继续当前操作
git cherry-pick --abort 放弃当前操作并恢复到操作开始前的状态

cherry-pick 复制的是一次改动，不会自动把原分支完整并入当前分支。某个修复若依赖更早的接口修改，应检查依赖提交，不能只因为冲突解决了，就认定移植后的逻辑正确。

忽略规则与未跟踪文件清理

命令 用途与影响
git check-ignore -v -- config.local.toml 查看未跟踪文件命中了哪份忽略规则；已跟踪文件默认不会作为忽略对象输出
git ls-files -- config.local.toml 检查该路径是否已经被跟踪
git rm --cached -- config.local.toml 从索引移除文件但保留当前本地副本，下一次提交将记录移除跟踪
git clean -nd -- tmp/ 预览指定目录中将被清理的未跟踪内容，不实际删除
git clean -fd -- tmp/ 真正清理指定范围的未跟踪内容，不包含标准忽略规则排除的文件
git clean -ndx -- build/ 预览清理指定范围，包含被忽略文件
git clean -fdx -- build/ 按相同范围真正删除，可能移除忽略的构建产物、环境文件等

.gitignore 主要约束未跟踪文件的纳入，不会让已经跟踪的文件自动退出版本控制。rm --cached 只解决后续跟踪问题，也不会清除该文件在历史提交中的内容。

clean 的 -n 表示预览，-f 表示允许实际删除，-d 用于未跟踪目录的清理，-x 表示不采用通常的忽略规则。预览与执行必须使用相同路径和选项，不能预览 tmp/ 后改成对整个仓库执行删除。参数细节见 git-clean。

标签与版本标识

命令 用途
git tag --list 列出本地标签
git tag -a v0.1.0 -m "release 0.1.0" 在当前提交上创建带说明的附注标签
git show v0.1.0 查看标签所标记的对象；附注标签还包含标签信息
git push origin v0.1.0 只推送指定标签；普通分支推送不等于推送全部标签
git tag -d v0.1.0 删除本地标签，不影响远程标签
git push origin --delete refs/tags/v0.1.0 删除远程同名标签，使用完整引用避免与分支同名时产生歧义

已经发布的标签可能被安装脚本、构建或使用者引用。需要修复发布内容时，通常应创建新版本，不应只考虑“把旧标签挪过去”是否能成功。

引用恢复与救援分支

命令 用途
git reflog --date=iso 查看本地 HEAD 的变更记录，定位切换、提交、reset 和 rebase 前后的位置
git reflog show main 查看指定本地分支引用的变更记录
git show <lost-commit> 检查找到的提交，确认内容是否符合预期
git branch rescue/frame-filter <lost-commit> 先为目标提交建立分支，保留它，再决定如何整合
git switch rescue/frame-filter 切换到救援分支进一步检查

HEAD@{1} 是本地 HEAD 的上一次记录，不一定是“撤销前的那个提交”；一次切换分支也会改变它。先读 reflog 并检查对象，再选择提交标识。

多工作目录开发

命令 用途与条件
git worktree list 查看当前仓库关联的工作目录及检出位置
git worktree add -b fix/typo ../blog-hotfix main 从本地 main 创建修复分支，并在新目录中检出；两个目录可以同时工作
git worktree remove ../blog-hotfix 移除已经不需要且状态干净的附加工作目录，不自动删除对应分支
git worktree prune -n 预览失效工作目录的管理记录清理，不删除实际项目内容
git worktree prune 清理失效的管理记录，不是删除正常工作目录的替代命令

worktree 共享仓库的对象与大部分引用，但有各自的工作区和索引。同一分支通常不能同时被两个工作目录检出；新增目录时应明确选择分支，不要用强制参数绕过不理解的占用状态。完整约束见 git-worktree。

回归问题的二分定位

命令 操作阶段
git bisect start 开始二分会话
git bisect bad <bad-commit> 标记一个已知存在问题的提交
git bisect good <good-commit> 标记一个已知正常的较早提交，Git 随后选择中间版本供测试
git bisect good、git bisect bad 根据当前检出版本的测试结果继续缩小范围
git bisect skip 当前版本无法可靠测试时跳过，不应将“构建不起来”直接标成同一个业务缺陷
git bisect run python -m unittest discover -s tests 自动运行项目测试，根据退出码继续定位；需替换为实际可用的测试命令
git bisect reset 结束会话，通常回到开始前检出的位置

自动测试应能区分正常、异常与无法测试：退出码 0 表示正常，1–127 中除 125 外表示异常，125 表示跳过，其他退出码会中止。命令不存在等环境错误也可能被误判为异常，因此应先验证测试命令本身。规则见 git-bisect。

改写远程历史的显式约束

只在已经确认远程分支允许改写时使用。<expected> 需要替换为已经检查并确认过的远程分支提交标识，不能不经检查就取一个新的值来使推送通过。

这条命令要求远程目标引用仍等于指定值，才允许用当前 HEAD 更新它。与省略预期值的形式相比，显式值不依赖后台 fetch 可能改动的远程跟踪引用；但它仍然只检查引用是否匹配，不能证明提交内容没有覆盖协作者的工作，也不能绕过服务端分支保护。git-push 对几种 lease 形式及后台抓取的影响有专门说明。

工作流检查清单

开始前看分支和工作区，提交前看暂存差异，合并前检查基线，撤销前确认需要保留的内容。Git 操作的可靠性来自这些检查形成的判断，而不只是记住了多少条命令。
